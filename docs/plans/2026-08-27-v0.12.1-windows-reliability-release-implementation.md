# v0.12.1 Windows Reliability & Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a reproducible and diagnosable Windows release of etcd Space Inspector, fix the large-Snapshot failure-observability gaps and frontend polling amplification, and make Windows large-Snapshot validation a release gate.

**Architecture:** Keep the existing single-binary architecture and M12 worker isolation model. Strengthen the worker/server diagnostic boundary so root causes survive into safe local logs, harden React polling so a slow backend cannot accumulate requests, unify verify/build/package entry points, and add a tag-driven GitHub Release workflow that produces a native Windows AMD64 ZIP with startup scripts and checksums. Large-Snapshot reliability is validated on native Windows rather than inferred from cross-compilation.

**Tech Stack:** Go 1.19+, React 19, TypeScript 5.8, Vite 6, PowerShell 7, GitHub Actions, `modernc.org/sqlite`, bbolt.

**Specs / existing design references:**
- `docs/specs/2026-08-18-m12-resilient-large-snapshot-analysis-design.md`
- `docs/specs/2026-07-17-windows-compatibility-design.md`
- `RELEASE.md`
- This plan extends the M12 design with release packaging, reproducible-build, polling, diagnostics, and native Windows release-gate requirements.

## Global Constraints

- Target release is `0.12.1`; do not move or recreate the existing `v0.12.0` tag.
- Follow the repository release naming convention: release branch `release/0.12.1`, tag `v0.12.1`.
- Native Windows release artifacts must be built and tested on `windows-latest`; Linux cross-compilation is not acceptable as release evidence.
- Preserve the current single executable architecture; frontend assets remain embedded in `etcd-analyzer.exe`.
- Do not introduce a required external database, service manager, installer, WSL, Git Bash, Make, or SQLite DLL.
- Preserve M12 security requirements: logs and diagnostics must not contain Kubernetes values, Secret/ConfigMap contents, tokens, certificates, HTTP request bodies, or raw external input paths.
- User-facing task errors remain safe and concise. Detailed causes belong in project-local diagnostic logs.
- Keep `MaxConcurrent` bounded to 1–2 and the existing worker/channel/SQLite batch hard limits unless a failing test proves a change is necessary.
- Avoid unrelated refactoring. `web/src/App.tsx` may be split only where required to isolate polling/log-panel behavior for testability.
- Use TDD for every behavior change: failing test first, smallest implementation, verification, then commit.
- Keep commits reviewable. Do not combine release automation, frontend polling, logging, and runtime changes in one commit.
- The release workflow must fail if `VERSION`, the git tag, and `web/package.json` disagree.
- The Windows ZIP must contain at minimum `etcd-analyzer.exe`, `start.cmd`, `start.ps1`, `config.example.yaml`, `README-Windows.md`, and `VERSION`.
- Release assets must include a SHA-256 checksum file.

## Current-State Findings the Implementation Must Address

1. The repository has tags, including `v0.12.0`, but has no GitHub Releases and no tag-driven release workflow.
2. `.github/workflows/ci.yml` verifies Windows/Linux/macOS, but only builds; it does not package or publish release assets.
3. `build.ps1` runs the frontend build but does not run `npm ci`, so a direct local build depends on the current `node_modules` state.
4. `cmd/etcd-analyzer/worker.go` receives the real error from `workerRunOperation` but writes only `worker operation failed`, discarding the cause needed for diagnosis.
5. `internal/worker/manager.go::logEvent` also discards `cause`, replacing it with a generic supervisor error.
6. M12 already isolates analysis in a worker and redirects worker stdout/stderr to per-run logs, so the correct fix is to preserve safe root-cause evidence inside this existing channel, not invent another logging subsystem.
7. The React application polls task/comparison state every two seconds with overlapping `fetch()` calls possible, has no request timeout/abort control, and couples task refresh to comparison refresh through `Promise.all`.
8. The task log panel also polls every two seconds without an in-flight guard.
9. M12 documentation explicitly states that native Windows 1.2 GB Snapshot validation was not completed, so large-Snapshot Windows support is not yet release-proven.
10. Existing `ETCD_ANALYZER_LONG_TESTS=1` coverage exercises a 20,000-revision semantic chain, but it is not a native Windows end-to-end 1 GB+ Snapshot release gate.

```text
1 GB+ analysis appears stuck
        |

        |       |
        |       +-- yes
        |

        |       |

        |       |

        |       |
        |       +-- yes --> slow analysis; inspect rate, DB/WAL, disk-free
```
