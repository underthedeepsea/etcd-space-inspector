# DB etcd 版本识别设计（0.6.0）

## 目标

导入 snapshot 或 `member/snap/db` 时，尽可能从数据库自身识别 etcd 集群版本，减少手动填写版本的需要；识别为受支持的 `3.4` 集群时自动启用现有 MVCC/Kubernetes 语义分析。

这项能力只回答“该数据库记录的集群版本族是什么”，不将其描述为完整的 etcd Server 二进制版本。

## 结论与范围

etcd 3.4 的成员信息会将集群版本写入 bbolt 的 `cluster` Bucket、`clusterVersion` Key。该值只足以确认主/次版本族；即使它呈现为 `3.4.0`，也不能推断运行中的二进制补丁版本为 `3.4.0`。

本版本只自动识别并启用已验证的 `3.4` 适配器。无法读取、格式异常、未支持版本或缺少预期 MVCC 结构的输入，继续只提供 Generic bbolt 结果，不做猜测。

不在本次实现的范围内：

- 从 DB 猜测精确补丁版本；
- 自动启用 3.5、3.6 等尚未验证的适配器；
- 从文件名、路径或任意 Bucket 名称推断版本；
- 导入日志或 Audit Log（属于后续 M6 日志关联工作）。

## 方案选择

考虑过三种方式：

1. 保持完全手动填写：最保守，但不能解决用户需要。
2. 仅用 Bucket 形状推断：覆盖面较大，但 `key` Bucket 并不足以证明版本，风险不可接受。
3. **读取集群版本元数据并二次验证结构**：只在 `cluster/clusterVersion` 明确为 `3.4`、且 MVCC `key` Bucket 存在时启动 3.4 分析。采用此方案。

## 数据模型与优先级

任务会保留以下版本证据：

| 字段 | 含义 |
| --- | --- |
| `etcdVersion` | 分析实际采用的版本：手动值可为完整 `3.4.x`，DB 识别值固定为版本族 `3.4`。 |
| `etcdVersionSource` | `manual`、`database_metadata` 或 `unknown`。 |
| `etcdVersionExact` | 仅在来自日志或手动输入且有完整补丁号时为真；DB 元数据识别始终为假。 |

优先级为：完整手动值 > DB 元数据 > 未知。即使给出手动值，也会读取 DB 元数据用于冲突提示；冲突时不覆盖手动选择，并在任务详情中暴露两份证据。

现有任务和已有 SQLite 数据库没有这些字段时视为 `unknown`，不会被重新分析或改变历史结论。

## 导入与分析流程

1. 安全复制 DB 输入后，以只读 bbolt 事务读取 `cluster/clusterVersion`。
2. 仅接受规范的语义版本值，归一化为主/次版本族；读取失败、值缺失或格式异常均记录为未知而非任务错误。
3. 写入 Manifest、SQLite 和任务 API，前端在任务详情和列表中显示版本、来源及“补丁号未知”提示。
4. MVCC 阶段在下列任一条件下启用 3.4 适配器：
   - 用户提供严格的 `3.4.x`；
   - DB 元数据确认版本族为 `3.4`。
5. 在启动解码前继续验证 `key` Bucket；验证失败则保存明确的 `semantic_decode_unavailable` 结论，不产生 MVCC/Kubernetes 语义结果。
6. 双 Snapshot 差分仅在两侧都已成功完成语义分析，且版本族相同（当前为 `3.4`）时输出语义增量。

## 安全与错误处理

- 检测器只读取固定 Bucket/Key，不遍历或持久化原始 Value。
- 数据库元数据属于不可信输入：长度设上限、严格验证文本格式，不解析任意内容。
- 打不开 DB 时仍由现有 bbolt 物理分析报告稳定错误；缺少版本元数据不是导入失败。
- UI、API、HTML 报告必须区分“DB 确认的集群版本族”和“精确 Server 版本未知”。

## 验证

- 单元测试：识别 `cluster/clusterVersion` 的 `3.4.x`/`v3.4.x`，拒绝不合法值和不支持版本。
- 服务测试：无手动版本的 3.4 fixture 自动写入 `database_metadata` 证据。
- MVCC 集成测试：DB 识别为 `3.4` 且存在 `key` Bucket 时，MVCC、Kubernetes 聚合和现有 M5 差分均可用。
- 降级测试：缺失元数据、缺失 `key` Bucket、3.5 元数据、手动值与 DB 元数据冲突均不输出未经验证的语义结论。
- 回归测试：手动 `3.4.x` 的现有任务行为不变。
